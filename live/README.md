# live

Webcam → MediaPipe → nearest indexed pose → the matching image.

## Run

```bash
npm install
npm run setup     # fetches the MediaPipe runtime + model
npm run dev
```

No configuration: the server looks in `../OUTPUT/` for a built index and reads
the images from `../INPUT/<dataset>`, following the dataset name recorded in
`index.json`. If several indexes exist, name one with
`BODY_DATASET=output-images npm run dev`.

Open http://127.0.0.1:5173 and press **start camera**.

`npm run setup` copies MediaPipe's wasm out of `node_modules` and downloads
`pose_landmarker_lite.task` into `public/mediapipe/`, so the app has no CDN
dependency at run time — an installation on a gallery network with no outbound
access still starts. Pass `full` or `heavy` for the larger models.

Use `localhost` or `127.0.0.1`, not a LAN IP: `getUserMedia` needs a secure
context and a bare IP is not one.

### Environment

All optional — the defaults follow the repository layout.

| | |
|---|---|
| `BODY_DATASET` | which index under `OUTPUT/` to serve. Needed only when there is more than one. |
| `BODY_INPUT` / `BODY_OUTPUT` | move the `INPUT/` and `OUTPUT/` directories elsewhere. |
| `BODY_ARTIFACTS` | serve an index directory outright, ignoring `OUTPUT/`. |
| `BODY_IMAGES_ROOT` | override where images are read from. |
| `BODY_THUMBS_ROOT` | override the thumbnails root. |

## How it fits together

Vite is the whole server. Two middlewares in [`vite.config.ts`](vite.config.ts)
serve things that live outside the project: `/api/*` for the index artefacts
from `OUTPUT/<dataset>/`, and `/img/*` for the source images from
`INPUT/<dataset>/`. Neither can be a static mount, because `INPUT/<dataset>` is
normally a symlink to another volume and which dataset is in play is decided at
run time. Requests are resolved with `realpath` and
checked for containment afterwards, so a symlink inside an images root cannot
be used to read the rest of the disk.

| | |
|---|---|
| [`encoding.ts`](src/encoding.ts) | The pose vector. A port of `encoding.py`, pinned to it by test. |
| [`pose.ts`](src/pose.ts) | Webcam plus MediaPipe, gathering 33 BlazePose landmarks down to 17 COCO ones. |
| [`searchIndex.ts`](src/searchIndex.ts) | Cosine recall over everything, then confidence-weighted re-rank of the shortlist. |
| [`smoothing.ts`](src/smoothing.ts) | Keeps the display watchable. |
| [`main.ts`](src/main.ts) | The loop. |

### Why smoothing is not optional

Nearest-neighbour lookup per frame, shown raw, strobes unwatchably. Two separate
problems, two mechanisms:

- Keypoints jitter a pixel or two between frames, which moves the query vector.
  An **exponential moving average** over the vector damps that, renormalised each
  time to stay on the unit sphere.
- Near the boundary between two equally good matches, the display flickers
  between them many times a second. **Hysteresis** on the result: a challenger
  has to be meaningfully better *and* the incumbent has to have been on screen
  for a minimum dwell.

Both are tunable at the top of `main.ts`.

### Performance

Search is a dot product against every row — 43k poses × 34 dims is about 1.5M
multiply-adds, well under a millisecond. That is why there is no VP-tree here;
Move Mirror needed one in 2018, a modern laptop does not. The shortlist for the
re-rank stage comes off a bounded min-heap rather than a sort, since sorting 43k
scores to look at 400 of them would be most of a frame's budget thrown away.

Detection, not search, is the cost. MediaPipe `lite` on the GPU delegate runs
comfortably at camera rate; `heavy` will not.

## Tests

```bash
npm test        # encoding parity + invariants
npm run build   # typecheck + production build
```

The parity tests check this implementation against golden vectors generated by
the Python indexer. They are the tests that matter: if the two encodings drift
apart, matching does not get worse, it becomes meaningless — and it looks like a
bad model rather than a bug. Regeneration instructions are in
[`../preprocessing/README.md`](../preprocessing/README.md).
